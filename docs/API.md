# API محلی NeoContract

نشانی پیش‌فرض `http://127.0.0.1:4173/api` است. درخواست و پاسخ، جز سند قرارداد، JSON هستند. برای بدنه، `Content-Type: application/json` بفرستید؛ سقف بدنه ۱ MiB است. احراز هویت و مدیریت کاربران در دامنه این دمو نیست و HTTP API از tenant نمایشی ثابت استفاده می‌کند. درخواست تغییردهنده دارای `Origin` باید با `Host` همان سامانه هم‌مبدأ باشد.

این راهنما مطابق [مسیرهای HTTP](../lib/http-api.mjs)، [ذخیره‌سازی](../lib/store.mjs)، [اعتبارسنجی](../lib/domain.mjs) و [اتصال‌ها](../lib/integrations.mjs) است. شناسه‌های مثال را از پاسخ واقعی جایگزین کنید.

## مسیرها

| روش و مسیر پس از `/api` | ورودی / خروجی |
| --- | --- |
| `GET /health` | `ok`, `backend`, `durable`, `migrations`, `counts` |
| `GET /bootstrap` | `catalog`, `customers`, `managers`, `templates`, `contracts`, `settings` |
| `GET /catalog` | مراکز با `services` تو‌در‌تو، فهرست تخت `services`، `slaProfiles`، `revenueModels` و مشخصات منبع |
| `GET /settings` | تنظیمات فضای کاری |
| `PUT /settings` | `workspaceName` الزامی، `defaultPaymentTerms` اختیاری؛ ارز `IRR` |
| `GET /customers` / `GET /managers` | فهرست مشتریان / مدیران حساب |
| `POST /customers` / `POST /managers` | ایجاد رکورد؛ پاسخ `201` |
| `PUT /customers/:id` / `PUT /managers/:id` | ویرایش رکورد |
| `DELETE /customers/:id` / `DELETE /managers/:id` | حذف در صورت نبود وابستگی؛ `{deleted:true,id}` |
| `GET /templates` | فهرست الگوها همراه نسخه‌ها و آخرین نسخه منتشرشده فعال |
| `POST /templates` | ایجاد الگو با نسخه پیش‌نویس؛ پاسخ `201` |
| `PUT /templates/:id` | ذخیره ویرایش با `revision` فعلی |
| `POST /templates/:id/publish` | انتشار نسخه بازبینی‌شده با `{revision,templateVersionId}` فعلی؛ تعارض `409` |
| `POST /templates/:id/archive` | بایگانی الگو؛ بدنه `{}`؛ `DELETE /templates/:id` نیز بایگانی می‌کند |
| `POST /contracts/preview` | اعتبارسنجی و تولید پیش‌نمایش، بدون ذخیره |
| `POST /contracts` | ثبت قرارداد و نسخه ثابت داده‌ها؛ پاسخ `201` |
| `GET /contracts` / `GET /contracts/:id` | فهرست / جزئیات قرارداد |
| `GET /contracts/:id/document` | سند HTML راست‌به‌چپ با `Content-Disposition: inline` |
| `POST /contracts/:id/advance` | پیشروی یک مرحله با کنترل وضعیت مورد انتظار |
| `POST /contracts/:id/amendments` | ثبت الحاقیه با `title`, `reason`, `body`؛ بازگشت جزئیات قرارداد |
| `POST /amendments` | همان عملیات الحاقیه، با `contractId` در بدنه |
| `POST /contracts/:id/neo-sync` | ایجاد یا بازیابی اتصال قرارداد و مراحل به Neo |
| `GET /integrations` | `neo`, `sync`, `database`؛ شامل ۲۰ برداشت اخیر فناسا |
| `POST /integrations/neo/run` | با `{}` بررسی اتصال؛ با `{contractId}` همگام‌سازی قرارداد |
| `POST /integrations/sync/run` | دریافت برداشت جدید فناسا در وضعیت `pending` |
| `POST /integrations/sync/approve` | اعمال برداشت با `{importId}` پس از بازبینی اپراتور |

پاسخ موفق مسیرهای دیگر `200` است. فهرست‌ها در این نسخه صفحه‌بندی یا فیلتر سمت سرور ندارند. برای جزئیات مشتری، مدیر حساب یا الگو، رکورد را از فهرست مربوط انتخاب کنید.

## مشتری و مدیر حساب

مدیر حساب: `name` الزامی؛ `role`, `email`, `phone` اختیاری؛ `status` برابر `active` یا `inactive` و پیش‌فرض `active` است. ایمیل غیرخالی باید معتبر باشد.

مشتری: `name` الزامی؛ `parentId`, `managerId`, `unit`, `industry` اختیاری؛ `status` یکی از `lead`, `active`, `paused`, `churned` و پیش‌فرض `active` است. `parentId` به مشتری مادر و `managerId` به مدیر حساب همان tenant اشاره می‌کند. درخت مشتری نمی‌تواند چرخه داشته باشد. مقدار خالی یا `null`، رابطه مادر یا مدیر را پاک می‌کند.

در `PUT` این دو موجودیت، نام را دوباره بفرستید و فیلدهایی را که باید حفظ شوند نیز ارسال کنید؛ فیلدهای اختیاری حذف‌شده از بدنه به مقدار خالی/پیش‌فرض برمی‌گردند. فیلدهایی مانند `id` و `verificationStatus` خروجی سیستم‌اند. `segment`, `contactName`, `email` در DTO مشتری دیده می‌شوند، اما این مسیر ذخیره مشتری آن‌ها را ویرایش نمی‌کند.

## الگو، نسخه و revision

ورودی الگو: `title`, `body`, `stages` الزامی هنگام ایجاد؛ `category`, `description`, `revenueModels` و `serviceCodes` اختیاری. هر مرحله شامل `id`, `name`, `role`, `slaDays`, `required`, `enabled` است؛ `id` حذف‌شده ساخته می‌شود. یک تا ۳۰ مرحله و حداقل یک مرحله فعال لازم است. `slaDays` عدد صحیح ۰ تا ۳۶۵، با پیش‌فرض ۲ است؛ مرحله الزامی نمی‌تواند غیرفعال باشد.

متغیرهای متن با قالب `{{title}}`: `title`, `party`, `customerName`, `managerName`, `amount`, `start`, `end`, `services`, `sla`, `paymentTerms`, `unit`, `contractNumber`, `owner`.

نام‌ها به حروف کوچک/بزرگ حساس‌اند. فاصله افقی دور نام، مانند `{{ title }}`، مجاز است؛ نام ناشناخته، ساختار ناقص یا اضافی آکولادها، نام نامعتبر مانند `{{title_name}}` و شکست خط داخل متغیر با `400` رد می‌شوند. همین اعتبارسنجی در ذخیره/انتشار الگو و در `body` سفارشی پیش‌نمایش/ثبت قرارداد اجرا می‌شود. متن عادی قرارداد می‌تواند چندخطی باشد؛ خود متغیر باید در یک خط قرار بگیرد.

- `id`: شناسه الگو؛ `templateVersionId`: شناسه UUID نسخه؛ `version`: شماره نسخه؛ `revision`: توکن مبهم کنترل هم‌زمانی. `revision` را محاسبه نکنید؛ عین پاسخ بفرستید.
- هر عضو فهرست الگوها، آخرین نسخه را در سطح اصلی، همه نسخه‌ها را در `versions` و نسخه منتشرشده جاری را در `currentPublishedVersion` دارد. آخرین نسخه ممکن است پیش‌نویس باشد و نسخه منتشرشده جاری همچنان قابل انتخاب بماند.
- `PUT` به `revision` سطح اصلی همان الگو نیاز دارد؛ نبودن یا قدیمی بودن آن `409` می‌دهد. فیلدهای محتوایی ارسال‌نشده از مقدار قبلی حفظ می‌شوند. ویرایش آخرین پیش‌نویس همان نسخه را تغییر می‌دهد؛ ویرایش پس از انتشار، پیش‌نویس نسخه بعدی می‌سازد.
- `title`, `category`, `description`, `revenueModels`, `serviceCodes` همراه `body` و `stages` متعلق به هر نسخه‌اند؛ ویرایش این اطلاعات در پیش‌نویس جدید، خروجی نسخه منتشرشده قبلی یا قراردادهای ثبت‌شده را تغییر نمی‌دهد. اطلاعات نسخه در فیلد JSON موجود `variable_schema.templateMetadata` ذخیره می‌شود و migration جدید لازم نیست؛ نسخه‌های قدیمی فاقد این فیلد از اطلاعات قبلی ثابت خوانده می‌شوند.
- انتشار به هر دو مقدار `revision` و `templateVersionId` از **آخرین نسخه بازبینی‌شده** نیاز دارد. سرور در همان تراکنش انتشار، آن‌ها را با آخرین نسخه مقایسه می‌کند؛ مقدار حذف‌شده، قدیمی یا شناسه نسخه نامطابق `409` می‌دهد. این مسیر برای انتشار دلخواه یک نسخه تاریخی نیست.
- انتشار موفق، همان نسخه را منتشر و اشاره‌گر نسخه جاری را عوض می‌کند. پس از ذخیره یا انتشار، مقادیر پاسخ تازه را نگه دارید. بایگانی همچنان بدنه `{}` می‌پذیرد و کنترل `revision` ندارد. الگوی بایگانی‌شده قابل انتشار یا انتخاب برای قرارداد جدید نیست.

نمونه ویرایش با `PUT /templates/:id`:

```json
{
  "revision": "<revision سطح اصلی از GET /templates>",
  "description": "شرح اصلاح‌شده الگو"
}
```

سپس، برای `POST /templates/:id/publish` مقادیر پاسخ ذخیره‌شده را بفرستید:

```json
{
  "revision": "<revision آخرین نسخه پس از بازبینی>",
  "templateVersionId": "<templateVersionId همان نسخه>"
}
```

در پاسخ `409`، فهرست الگوها را دوباره دریافت و نسخه جدید را بازبینی کنید. صرفاً تعویض توکن و تلاش خودکار می‌تواند نسخه‌ای را منتشر کند که کاربر ندیده است. در حضور پیش‌نویس جدید، مقادیر `currentPublishedVersion` برای انتشار آن پیش‌نویس معتبر نیستند.

## پیش‌نمایش و ثبت قرارداد

این دو مسیر یک ساختار ورودی دارند. `templateId`, `customerId`, `title`, `amount`, `owner`, `start`, `end`, `paymentTerms` الزامی‌اند. با حذف `templateVersionId`، نسخه منتشرشده جاری انتخاب می‌شود؛ برای انتخاب صریح، UUID نسخه منتشرشده را بفرستید. `managerId` اختیاری است و در نبود آن مدیر مشتری انتخاب می‌شود؛ مدیر غیرفعال پذیرفته نمی‌شود.

```json
{
  "templateId": "<شناسه الگو>",
  "templateVersionId": "<شناسه نسخه منتشرشده>",
  "customerId": "<شناسه مشتری>",
  "title": "قرارداد خدمات زیرساخت",
  "amount": 120000000,
  "owner": "واحد قراردادها",
  "start": "2026-10-01",
  "end": "2027-09-30",
  "paymentTerms": "پرداخت ماهانه طبق صورت‌حساب تأییدشده",
  "services": [
    {
      "code": "<کد از catalog.services>",
      "slaTier": "<کد از catalog.slaProfiles>",
      "revenueModel": "<کد از catalog.revenueModels>",
      "delivery": "managed",
      "quantity": 1,
      "unitPrice": 10000000
    }
  ],
  "idempotencyKey": "<کلید یکتای این درخواست ثبت>"
}
```

فیلدهای اختیاری دیگر: `party` (پیش‌فرض نام مشتری)، `unit` (پیش‌فرض واحد مشتری)، `body` و `stages`. مراحل سفارشی باید همه مراحل الزامی نسخه انتخابی را با همان `id` و `role`، فعال و الزامی و با همان ترتیب نسبی حفظ کنند. جابه‌جایی یک مرحله الزامی جلوتر از مرحله الزامی قبلی با خطای 400 رد می‌شود؛ افزودن یا جابه‌جایی مراحل اختیاری میان آن‌ها مجاز است. تاریخ‌ها میلادی `YYYY-MM-DD` هستند؛ تاریخ پایان نمی‌تواند قبل از شروع باشد.

هر سرویس به `code` معتبر، `slaTier` معتبر، `unitPrice` صریح و `delivery` صریح نیاز دارد؛ `tier` نیز نام جایگزین ورودی SLA است. `revenueModel` حذف‌شده از منبع می‌آید؛ `quantity` پیش‌فرض ۱ و حداقل ۰٫۰۰۰۱ است. `delivery` یکی از `self_service`, `automatic`, `managed`, `project`, `on_request` است و از منبع به‌صورت خودکار جایگزین نمی‌شود. حداکثر ۲۰۰ سرویس بدون کد تکراری پذیرفته می‌شود؛ فهرست خالی مجاز است.

مبلغ‌ها ریال‌اند. `amount` مبلغ توافقی مستقل است و از جمع ردیف‌ها یا تعرفه منبع محاسبه نمی‌شود. `amount` و `unitPrice` باید عدد یا رشته عددی صریح باشند؛ صفر مجاز است، اما مقدار حذف‌شده، `null` یا رشته خالی رد می‌شود. انتخاب SLA متفاوت از پیش‌فرض منبع به عنوان `negotiated-selection` ثبت می‌شود. خروجی پیش‌نمایش شامل `document` و `snapshot` است؛ ثبت، شماره قرارداد، مراحل، تاریخچه و سند را ذخیره می‌کند. اطلاعات مشتری، الگو، سرویس، SLA و نرخ‌نامه منبع در snapshot ثابت می‌مانند.

`idempotencyKey` فقط برای ثبت است و حداکثر ۱۲۰ نویسه دارد. تکرار همان کلید با همان شیء ورودی JSON، قرارداد قبلی را برمی‌گرداند؛ محتوای متفاوت `409` می‌دهد. کلید و ترتیب فیلدهای بدنه را در تلاش مجدد حفظ کنید؛ هش از `JSON.stringify(input)` ساخته می‌شود.

## پیشروی و الحاقیه

پیش از پیشروی، جزئیات تازه قرارداد را بگیرید. برای قرارداد `draft` بفرستید:

```json
{"expectedStatus":"draft","expectedStepId":null,"comment":"شروع بررسی"}
```

در مراحل بعد، `expectedStatus` برابر `status` فعلی و `expectedStepId` برابر **`stepId` مرحله دارای `status:"active"`** است؛ از `stages[].id` که کلید منطقی مرحله است استفاده نکنید. `comment` اختیاری و حداکثر ۲۰۰۰ نویسه است. ناهماهنگی وضعیت/مرحله پاسخ `409` می‌دهد؛ جزئیات را تازه‌سازی و تصمیم را دوباره بررسی کنید.

اولین پیشروی، نخستین مرحله را فعال می‌کند و بر اساس نقش آن، قرارداد را `in_process` یا `awaiting_signature` می‌کند. هر درخواست بعدی مرحله فعال را تکمیل و مرحله بعد را فعال می‌کند؛ مرحله با نقش دقیق `signatory` یا نام قدیمی «صاحب امضا»/«صاحب امضاء»، وضعیت قرارداد را `awaiting_signature` می‌کند؛ عنوان مرحله معیار تشخیص نیست. پایان همه مراحل، وضعیت قرارداد را `active` می‌کند. قرارداد خارج از `draft`, `in_process`, `awaiting_signature` قابل پیشروی نیست.

رویدادهای جدید `workflow_advanced` شامل `templateVersionId`, `completedStep` و `nextStep` هستند. دو فیلد مرحله، `null` یا شیء دارای `id` (کلید منطقی)، `stepId` (UUID اجرایی)، `name` و `role` هستند. شروع فرآیند `completedStep:null` و پایان فرآیند `nextStep:null` دارد. سوابق قبلی بدون تغییر باقی می‌مانند.

الحاقیه به `title`, `reason`, `body` غیرخالی نیاز دارد؛ سقف متن ۲۰٬۰۰۰ نویسه است. شماره الحاقیه خودکار تخصیص می‌یابد و اصل snapshot قرارداد بازنویسی نمی‌شود.

## واردات فناسا و Neo

`POST /integrations/sync/run` با بدنه `{}` دریافت رسمی را اجرا می‌کند. موفقیت دریافت، پاسخ شامل `id`/`importId`, `status:"pending"`, `counts`, `sources`, `warnings`, `sha256`, `httpStatus` می‌دهد و هنوز کاتالوگ فعال را تغییر نمی‌دهد. گزارش را بازبینی کنید، سپس شناسه را به `POST /integrations/sync/approve` بفرستید:

```json
{"importId":"<شناسه برداشت بازبینی‌شده>"}
```

تأیید اپراتور وضعیت برداشت را `approved` می‌کند و کاتالوگ و نگاشت SLA را در یک تراکنش اعمال می‌کند. تکرار تأیید برداشت تأییدشده، همان نتیجه را برمی‌گرداند. داده فعال همچنان `verificationStatus:"http-observed-unverified"` دارد؛ این تأیید، تأیید حقوقی نیست. دریافت ناقص/ناموفق یا خطای اعمال، داده فعال قبلی را حفظ می‌کند. پس از اعمال، `GET /catalog` را دوباره بخوانید؛ قراردادهای قبلی تغییر نمی‌کنند.

وضعیت بازبینی اپراتور مستقل از وضعیت مشاهده منبع است. پاسخ‌های `GET /catalog` و `GET /bootstrap` در کاتالوگ، و `GET /integrations` در `sync`، فیلد `operatorReview` دارند:

```json
{
  "status": "approved",
  "importId": "<شناسه برداشت فعال>",
  "reviewedAt": "2026-09-30T12:00:00.000Z"
}
```

این مقدار از رکورد `approved` دارای `reviewed_at` در همان tenant و مرتبط با `catalog.importId` محاسبه می‌شود. داده اولیه، شناسه حذف‌شده/نامعتبر، رکورد فاقد زمان بازبینی یا متعلق به tenant دیگر، مقدار `{"status":"unreviewed","importId":null,"reviewedAt":null}` می‌دهد. زمان و وضعیت موجود در داده خام کاتالوگ، جایگزین رکورد تأیید نمی‌شود. دریافت جدید `pending` یا `failed`، وضعیت بازبینی کاتالوگ فعال قبلی را تغییر نمی‌دهد؛ برای نمایش وضعیت فعلی از آخرین ردیف تاریخچه واردات نتیجه‌گیری نکنید.

`operatorReview.status:"approved"` یعنی اپراتور این برداشت را بازبینی و اعمال کرده است؛ `verificationStatus` همچنان `http-observed-unverified` می‌ماند. این وضعیت، تأیید حقوقی قرارداد یا راستی‌آزمایی مستقل منبع نیست و مشاهدات سرویس‌ها یا snapshot قراردادهای قبلی را تغییر نمی‌دهد.

بررسی اتصال Neo ممکن است HTTP `200` همراه `status:"unavailable"` بدهد؛ فیلد وضعیت را بررسی کنید. همگام‌سازی قرارداد، کار مادر و مراحل فعال، وابستگی و گزارش وضعیت می‌سازد و نتیجه شامل `parentItemId`, `stages`, `projectId`, `url`, `syncedAt`, `status:"synced"` است. کلیدهای ثابت برای تلاش مجدد استفاده می‌شوند و اتصال ذخیره‌شده در `contract.neoBinding` قابل مشاهده است. تنظیم پروژه از `planning/neo-binding.json` می‌آید؛ این عملیات پروژه جدید نمی‌سازد.

خروجی جدید اتصال قرارداد، `templateId`, `templateVersionId`, `templateVersion` و `workflowStatus` قرارداد را نیز دارد. هر ردیف `stages` علاوه بر فیلدهای قبلی، `stepId`, `role`, `required`, `sourceSequence`, `executionSequence` و `workflowStatus` دارد. `status` ردیف همچنان وضعیت مستقل کار Neo است؛ اتصال آن را به‌صورت خودکار پیش نمی‌برد. وابستگی مفقود غیرقابل‌اصلاح یا وابستگی اضافی با `409` و `code:"neo_workflow_deviation"` گزارش می‌شود؛ پیش از تلاش مجدد، مسیر Neo را بازبینی کنید.

## خطاها

شکل خطا `{ "error": "پیام قابل نمایش", "code": "validation" }` است؛ `code` می‌تواند `not_found`, `internal` یا `neo_unavailable` نیز باشد. `400` ورودی نامعتبر، `403` مبدأ نامعتبر، `404` رکورد/مسیر ناموجود، `409` تعارض نسخه/وضعیت یا وابستگی داده، `413` بدنه بزرگ، `502` خطای دریافت/اتصال، `503` نبود توکن لازم و `500` خطای داخلی را نشان می‌دهد. برای تنظیم اجرا و نگهداری داده، [راهنمای عملیات](OPERATIONS.md) را ببینید.
